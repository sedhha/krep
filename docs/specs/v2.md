# Registry V2 — Admin Panel, Organisations, Products, Users, Pluggable Auth

Status: agreed design, ready for task breakdown. Builds on `docs/specs/v1.md`; V1 stays in force unless this document says otherwise. 

## 0. How to read this spec

- **Must** = required for V2. **Later** = designed for, not built.
- Everything runs locally from docker compose and environment variables. No cloud dependency in V2.

## 1. Intent and scope

V1 is the registry engine. Onboarding a customer is still an ops task. V2 adds a **platform admin panel** and the identity model around it, so a platform admin can plug in an organisation and hand it over; the organisation's own admin then runs everything inside it.

Must:

1. **Hierarchy:** platform -> organisation -> product.
2. **Hand-over model:** the platform admin only creates an organisation, sets its admin policy and attaches the first admin user. After that the **org admin** can do anything inside the organisation and nothing outside it (products, auth, resources, policies, links, members).
3. **Users and login:** username + password login through Better Auth (Next.js BFF, same Postgres, separate `auth` schema); anyone can sign up, an org admin attaches users to the organisation and its groups; one user can belong to several organisations; platform admins are users granted through an API. More login methods are Better Auth configuration later.
4. **Pluggable organisation authentication** for the organisation's own API callers (HMAC secret first), overridable per product, secrets encrypted with a local key.
5. **Policy-only access:** nothing is visible by default. A resource can have several policies per action. A built-in `open-to-all` policy opens a resource at org, product or global reach.
6. **Resource scope:** org-level, product-level, global; scope is editable.
7. **Links** across scopes by an explicit rule table.
8. **Organisation lifecycle:** suspend, then scheduled hard delete after a grace period, with legal hold.
9. **Admin panel UI** (simple; Next.js as a thin BFF): organisations, users and members, products, auth, policies (visual rule builder), agents.

Non-goals (Later): JWKS organisation adapter, SSO / email-link / 2FA login methods (Better Auth configuration), email verification, KMS adapters, skills/prompts/context documents in the UI, scheduled orphan-account cleanup, data-residency routing, billing and usage dashboards.

Anti-goals: a public admin surface; secrets or credentials readable through any FastAPI route; a second policy engine; business logic or authorization in the Next.js layer; customer data becoming visible to another organisation without a platform admin's approval.

## 2. Concepts

| Term                  | Meaning                                                                                                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Platform admin        | A user listed in `platform_admins`, or a caller with the env platform key. Creates organisations and their first admin, manages users and global content. |
| Organisation          | A customer. **The same thing as a V1 tenant** (`organizations.id = tenant_id` everywhere).                                                                |
| Platform organisation | One reserved organisation (`is_platform`, slug `platform`). Owns platform-created global content. Not a customer.                                         |
| Org admin             | A caller who satisfies the organisation's `registry-admins` policy. Full control inside that organisation only.                                           |
| Product               | A named sub-scope inside an organisation.                                                                                                                 |
| Scope                 | Per resource: `org`, `product` or `global`. A column on `registry`, not a separate table.                                                                 |
| Agent runtime         | **Not a separate entity.** An `agent` resource at any scope (product, org or global).                                                                     |
| User                  | A Better Auth account (`auth` schema), referenced by id (text). Belongs to organisations through memberships.                                             |
| Membership            | (user, organisation, groups). The groups are what org policies match (`"billing" in token.groups`).                                                       |
| Auth config           | How an organisation (or one product) verifies its **own API callers**: adapter type, non-secret config, encrypted secret.                                 |
| Open-to-all policy    | Reserved always-satisfied policy, one per organisation.                                                                                                   |

### 2.1 Tenancy and scope: one set of tables

There is **no second table** for global content. Every resource lives in `registry` (and its version/subtype/link tables) with `tenant_id` = its owning organisation, and a `scope` column says who may see it:

| `scope`   | `product_id` | Owner                                         | Reach                                              |
| --------- | ------------ | --------------------------------------------- | -------------------------------------------------- |
| `org`     | null         | any organisation                              | the owning organisation (any product, or none)     |
| `product` | set          | any organisation                              | callers of that product only                       |
| `global`  | null         | any organisation, **set by a platform admin** | callers of every organisation, subject to policies |

- Search, get, bundle, linking and publishing are the same code for all three; the only difference is one predicate (4.2) and one extra read-only RLS rule.
- `tenant_id` stays `NOT NULL` and always names the **owner**. "Global" is a scope, not a missing tenant: this keeps foreign keys, unique constraints and RLS simple, and flipping a resource back from global needs no data move because the owner never changed
- Scope is **editable** in both directions (rules in 4.5): `product` <-> `org` by the owner's admins; `global` is set by a platform admin only, and the owner can demote it back unless other organisations depend on it.
- **Privacy guard:** a customer resource becomes visible to other organisations only through a platform admin's explicit action (DB trigger, audit row), never through an ordinary edit.

## 3. Identity

### 3.1 Two kinds of caller, one evaluation document

| Caller                  | Credential                                                                                                   | Evaluation document `token`                                                                                                                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Panel user              | `Authorization: Bearer <login JWT>` minted by the Better Auth service (3.4) and forwarded by the Next.js BFF | `{"sub": "<auth user id>", "username": "...", "groups": [<membership groups>]}` built **per request**: `sub`/`username` from the verified JWT, `groups` from our `memberships` table, so group and membership changes apply immediately |
| Organisation API caller | `Authorization: Bearer <jwt>` verified by the organisation's (or product's) auth config (section 5)          | the verified claims                                                                                                                                                                                                                     |
| V1 callers              | issuer JWKS or `X-API-Key` without selector headers                                                          | unchanged                                                                                                                                                                                                                               |

Policies are the same for all of them; a capability rule can mix both: `"org-admin" in token.groups || "admins" in token.roles`. A login JWT is recognised by its `iss` (`KREP_LOGIN_ISSUER`); an organisation auth config may not register that issuer.

### 3.2 Selector headers

```text
X-Org: acme              required in selector mode (organisation slug)
X-Product: billing-bot   optional (product slug); absent = organisation-level request
```

1. `X-Org` present -> selector mode (V1 modes are not tried). Unknown, suspended or pending-delete organisation, unknown product, or failed credential -> identical `401 unauthenticated`.
2. **`X-Product` is nullable.** Without it the request is organisation-level: it sees `org` and `global` resources, never `product` ones. Management lists for admins cover all products (filter `?product=`).
3. Credential check: a login JWT -> verified through JWKS, `sub` not in `disabled_users`, a membership of that user in the organisation (or platform admin) -> else `401`; any other Bearer JWT -> the product's auth config if one exists, else the organisation's.
4. `var.product_id` is available in rules (null when absent). Tenant always comes from the resolved organisation, never from a claim or body.

### 3.3 Platform admin

- A user listed in `platform_admins`, **or** a caller with `X-Platform-Key` equal to `KREP_PLATFORM_ADMIN_KEY` (>= 32 chars, constant-time compare). Env key unset -> key auth is off.
- Granting: `PUT /v1/admin/platform-admins/{user_id}` (platform key or an existing platform admin) or, for bootstrap, `krep platform-admin grant --username <username>` (owner role; resolves the id from the auth schema). Flow: the person signs up in the panel, then is granted.
- Platform routes (`/v1/admin/...`) accept only a platform admin. Inside an organisation (`X-Org` + platform identity) a platform admin is `can_admin`; this is how global content is managed (`X-Org: platform`).

### 3.4 Panel login: Better Auth behind a thin Next.js BFF

```text
browser -> Next.js (UI + BFF + Better Auth) -> FastAPI /v1
              |  session cookie (HttpOnly)       |  Authorization: Bearer <login JWT>, X-Org, X-Product
              +--> Postgres schema `auth`        +--> verifies via JWKS, loads memberships from public schema
```

- **Better Auth owns identity only:** users, credentials, sessions, login methods. It lives in `ui/` (the Next.js app), uses the **same Postgres** in a separate `auth` schema with its own role (`krep_auth`) and its own migration (`npx @better-auth/cli migrate`) that runs **before** Alembic. Alembic never touches `auth`.
- **Plugins used:** `username` (username + password login), `admin` (create, ban, reset password, list users), `jwt` (login JWTs and JWKS). **Not used:** `organization`; organisations, memberships, groups and policies stay in our tables so RLS and the policy engine have one source of truth.
- **Login adapters:** password in V2. SSO/OIDC, magic link and 2FA are later configuration of Better Auth, not code in FastAPI. Better Auth keeps an `email` field even for username login; email verification stays off in V2.
- **Sign-up is open** (`KREP_ALLOW_SIGNUP`, default true locally): anyone can create an account, but an account with no membership can do nothing (`401` on every organisation). Better Auth's rate limiting is on. Flag for Security review before the panel is reachable from outside a private network.
- **BFF to FastAPI:** Next route handlers proxy `/api/v1/*` to FastAPI with the user's login JWT. The JWT lifetime is `KREP_LOGIN_JWT_TTL_SECONDS` (default 3600, so sessions are not refreshed mid-use). FastAPI verifies it through `KREP_LOGIN_JWKS_URL` using the V1 JWT code and checks `iss`/`aud`.
- **Instant disable despite the 1 h JWT:** banning a user also writes `disabled_users` (through `POST /v1/admin/users/{id}/disable`), which FastAPI checks on every request. Removing a membership or changing groups is already instant because they are read per request. The remaining lag (password change, logout) is up to the JWT lifetime.
- **The BFF holds no registry or policy logic** and is not trusted for authorization: FastAPI enforces every rule. Next.js middleware is never used for authorization (it has had bypass CVEs). Next only hides controls using `GET /v1/me`.
- **User creation:** anyone can sign up; a platform admin can also create users through the admin plugin. **Associating a user with an organisation and its groups is the org admin's job** (3.5). No cross-schema foreign keys: `memberships.user_id` is the Better Auth user id as text.
- **User lookup for org admins:** FastAPI may read a narrow view `public.auth_users (id, username, email, name)` over the auth schema, exact-match only, no listing, generic `404` when not found. Password and account tables are not readable by `krep_app`.
- Better Auth is a young 1.x library: pin its version; the first UI task starts with a short spike on schema placement (`auth` search path), the `jwt` plugin and the `username` plugin together.
- FastAPI-native auth (Argon2 + own sessions) was rejected in favour of Better Auth because of the SSO and login-adapter roadmap.

### 3.5 Roles: who can do what

| Action                                                               | Platform admin         | Org admin (own org only)                           | Org writer / reader                       |
| -------------------------------------------------------------------- | ---------------------- | -------------------------------------------------- | ----------------------------------------- |
| Create / suspend / schedule-delete organisation, legal hold          | yes                    | no                                                 | no                                        |
| Create users (sign-up is open), grant platform admin, disable a user | yes                    | no                                                 | no                                        |
| Attach an existing user to the organisation, set groups              | yes (any organisation) | yes (own organisation, by exact username or email) | no                                        |
| Set org capability policies; set first org admin                     | yes                    | yes                                                | no                                        |
| Products, org and product auth configs                               | yes                    | yes                                                | no                                        |
| Policies, resources, versions, links in the org                      | yes                    | yes                                                | by `registry-writers` / resource policies |
| Move a resource to `global` scope                                    | yes (approval)         | no (can demote their own back)                     | no                                        |
| Global content owned by the platform organisation                    | yes (write)            | read only, by policy                               | read only, by policy                      |

"Org admin" is exactly `can_admin` from V1 (`registry-admins` policy). Policies attach to users **through groups**: an org admin puts a user in groups (membership) and writes policies over `token.groups`. Per-user policy grants are not a separate mechanism.

### 3.6 Capability policies

Created with the organisation, editable by org admins (platform admin can reset): `registry-admins`, `registry-writers`, `registry-readers`, `open-to-all`. Defaults for panel users:

| Policy             | Default rule                                                                              |
| ------------------ | ----------------------------------------------------------------------------------------- |
| `registry-admins`  | `"org-admin" in token.groups`                                                             |
| `registry-writers` | `"org-admin" in token.groups \|\| "writer" in token.groups`                               |
| `registry-readers` | `"org-admin" in token.groups \|\| "writer" in token.groups \|\| "reader" in token.groups` |

The platform admin may supply different rules at creation (for API callers with their own claims). Fail closed: a missing or unsatisfied capability policy means no access. Lock-out recovery stays the platform admin's `reset`.

## 4. Policies on resources (replaces V1 `visibility`)

### 4.1 Several policies per action

A resource has any number of policies per **action**, in a join table. A caller is allowed an action if **any** attached policy for that action is satisfied (OR); AND/NOT live inside a policy's rule. Maximum 10 policies per resource and action (limit key `max_policies_per_resource_action`).

| Action   | Governs                                                                            |
| -------- | ---------------------------------------------------------------------------------- |
| `read`   | search, get-by-id, bundle, and creating a link that targets the resource           |
| `manage` | edit, publish, archive, delete, accept/reject/unlink links, creating links from it |

Rules:

- No `read` policy attached = invisible to everyone except the creator and org admins. There is no `visibility` column.
- The creator always reads and manages their own resources; org admins manage any resource of their organisation. Neither is policy-driven.
- A caller also needs the organisation capability (`registry-readers` to read, `registry-writers` to manage) **and** one satisfied resource policy.
- `open-to-all` attached as a `read` policy makes the resource visible to everything its scope reaches (4.2).
- Actions are rows, not columns: adding `link` or `analyze` later needs no schema change.

### 4.2 Discovery predicate (V1 section 8.4, extended)

```sql
WITH sat AS MATERIALIZED (
  SELECT p.id FROM access_policies p
  WHERE (p.tenant_id = :tenant
         OR p.id IN (SELECT rp.policy_id FROM registry_policies rp JOIN registry g ON g.id = rp.registry_id WHERE g.scope = 'global'))
    AND (p.kind = 'open' OR jsonb_path_match(:doc::jsonb, p.compiled_path, :vars::jsonb, true))
)
SELECT ... FROM registry r
WHERE (r.tenant_id = :tenant OR r.scope = 'global')
  AND (r.scope <> 'product' OR r.product_id = :product)
  AND r.status = 'published'
  AND EXISTS (SELECT 1 FROM registry_policies rp
              WHERE rp.registry_id = r.id AND rp.action = 'read'
                AND rp.policy_id IN (SELECT id FROM sat))
```

`:vars` gains `product_id`. Creator and admin branches are OR-ed in as in V1. Cost still scales with the number of policies, not resources. The `EXISTS` is covered by the primary key `(registry_id, action, policy_id)`.

### 4.3 Global content: what other organisations can read

Extra `SELECT`-only RLS rules, nothing else:

- `registry` rows with `scope = 'global'`, and the version, subtype and file rows of those resources;
- the `access_policies` and `registry_policies` rows **referenced by global resources** (so their rules can be evaluated against the caller's token).

Writes stay tenant-isolated: global rows are written only under their owner's tenant context. Setting `scope = 'global'` is allowed on any organisation's resource **only in a transaction opened by a platform admin** (`app.platform_admin = on`, enforced by a trigger); the owner keeps ownership and can demote the resource back (4.5). `tenant_id` never changes, so nothing is moved or copied.

### 4.4 Migration of V1 data

| V1                            | V2                                             |
| ----------------------------- | ---------------------------------------------- |
| `restricted`, `policy_id = P` | `registry_policies(read, P)`                   |
| `tenant`                      | `registry_policies(read, <org's open-to-all>)` |
| `private`                     | no policy rows (creator and admins only)       |

All existing resources get `scope = 'org'`. V1 tenants are backfilled into `organizations` (slug `tenant-<first 8 of uuid>`, renamable). Existing reserved policies stay; `registry-readers` is created equal to `open-to-all` for migrated tenants so "every authenticated caller can read" is unchanged. Then `visibility` and `policy_id` are dropped.

### 4.5 Changing scope

| Change                      | Who                                 | Rule                                                                                   |
| --------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------- |
| `product` <-> `org`         | anyone who can manage the resource  | none beyond product existing                                                           |
| `org`/`product` -> `global` | platform admin only                 | the resource must be published; audit row written                                      |
| `global` -> `org`           | owner's org admin or platform admin | `409 resource_in_use` while any other organisation links to it or pins a version of it |

## 5. Organisation authentication (for the organisation's own API callers)

Separate from panel login (3.4). An organisation configures how **its** callers (apps, agent runtimes, its users' tokens) authenticate.

### 5.1 Adapter interface (`src/krep/auth/`)

```python
class AuthAdapter(Protocol):
    type: ClassVar[str]
    config_model: ClassVar[type[BaseModel]]
    secret_fields: ClassVar[tuple[str, ...]]
    def verify(self, token: str, config: BaseModel, secrets: Mapping[str, str]) -> Mapping[str, Any]: ...
```

`GET /v1/admin/auth-adapters` returns each adapter's JSON Schema and secret fields; the UI renders the form from it, so a new adapter needs no UI change.

### 5.2 HMAC adapter (`hmac`)

| Field                | Secret | Notes                                                                                |
| -------------------- | ------ | ------------------------------------------------------------------------------------ |
| `secret`             | yes    | >= 32 bytes, write-only                                                              |
| `algorithms`         | no     | subset of `HS256`, `HS384`, `HS512`, default `["HS256"]`; `none` and non-HS rejected |
| `audience`, `issuer` | no     | optional exact match on `aud` / `iss`                                                |
| `user_claim_path`    | no     | default `["sub"]`                                                                    |
| `allow_principal`    | no     | default false (V1 meaning)                                                           |

`exp` required, 30 s leeway, header algorithm must be allowed, secret never logged.

### 5.3 Inheritance

Effective config = the product's if it has one and the request selected that product, else the organisation's. An organisation with no config accepts no Bearer API callers in selector mode (panel users with a login JWT still work).

### 5.4 Secret encryption

`cryptography` Fernet via `MultiFernet`. `KREP_ENCRYPTION_KEYS` = comma list `<key_id>:<urlsafe-base64-32-bytes>`; first encrypts, all decrypt (rotation = prepend a key, re-save). `auth_configs.secret_enc` + `key_id`. Replaceable by a KMS provider behind the same `encrypt/decrypt` interface. `krep keys generate` prints a key. Secrets are never returned (`secret_set`, `key_id`, `rev` only) and never logged; decrypted verifiers are cached by `(config id, rev)` for 60 s.

## 6. Links across scopes

V1 link rules (`link_rules`: types, relation, acceptance) stay. A new table decides which **scope pairs** may link, so future pairs are data, not code:

| source scope -> target scope   | V2        | Notes                                                                                                                                            |
| ------------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| org -> org                     | allowed   | same organisation                                                                                                                                |
| org -> product, product -> org | allowed   | same organisation                                                                                                                                |
| product -> product             | allowed   | same product only                                                                                                                                |
| global -> global               | allowed   |                                                                                                                                                  |
| org / product -> global        | allowed   | an organisation's agent uses a global skill; cross-tenant mechanics in 6.1                                                                       |
| **global -> org / product**    | **never** | global content must not depend on customer data; a trigger rejects `allowed = true` for these rows, so a future change is a deliberate migration |

Creating a link requires `manage` on the source, `read` on the target and an allowed scope pair. Bundles keep V1 semantics: dependencies are included because the source's publisher vouched for them, regardless of the caller's own discovery rights, so an org agent linked to a product-level or global skill loads in any product.

### 6.1 Cross-tenant links (org/product -> global)

- The link and its frozen `registry_version_deps` rows live in the **source** tenant; they point at a global version in another tenant. Reading that version works through the global read rules (4.3).
- **Retention and delete protection:** foreign keys stay `RESTRICT`, so a global version or resource that another organisation depends on cannot be pruned or deleted. The attempt returns `409 version_in_use` / `409 resource_in_use`. Referrers in other organisations are hidden by RLS, so the response lists them only for a platform admin (through a `SECURITY DEFINER` function returning organisation slugs and counts); others get a count.
- Demoting a global resource (4.5) and purging an organisation that owns referenced global resources are blocked the same way.
- Publishing a global skill version never changes frozen dependencies of other organisations' versions (V1 acceptance test 20 holds across tenants).

## 7. Organisation lifecycle and deletion

`organizations.status`: `active` -> `suspended` -> `pending_delete` -> (purged).

| Step            | Effect                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Suspend         | immediate `401` for every request of that organisation; data kept; reversible                                                                                                                                                                                                                                                                                                                                                                                         |
| Schedule delete | `POST /v1/admin/organizations/{id}/schedule-delete {grace_days}`; status `pending_delete`, `delete_after = now() + grace`; reversible with `cancel-delete`                                                                                                                                                                                                                                                                                                            |
| Legal hold      | `legal_hold = true` blocks purge until cleared                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Purge           | background job (`krep jobs purge-due`, run by cron / a scheduled task; optional in-process timer locally) deletes **all** rows of the tenant in dependency order in one transaction through the owner-role function `purge_organization(uuid)`: resources, versions, subtypes, files, links, policies and history, synonyms, products, auth configs (secrets) and memberships. `admin_audit_log` keeps only organisation id, action and timestamp; `detail` is nulled |
| Purge blockers  | the purge is refused, and reported in the job output and the console, while other organisations link to its global resources or `legal_hold` is set                                                                                                                                                                                                                                                                                                                   |

Accounts live in the `auth` schema and are not organisation data. After a purge, users with no memberships and not platform admins are orphans; the platform admin deletes them through the console (Better Auth admin API). Scheduled orphan cleanup is Later.

Grace period: platform default `KREP_ORG_DELETE_GRACE_DAYS=30`, adjustable per request up to 90.

**Compliance notes (not legal advice; needs Legal / DPO review before relying on them):**

| Regime                              | What it implies for this design                                                                                                                                                                                                                                                                                                                          |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EU / UK GDPR                        | We act as processor for the organisation (controller): delete or return data on termination (Art. 28(3)(g)); erasure requests expected "without undue delay", normally within one month (Art. 17, 12(3)). A 90 day grace is hard to defend against that; 30 days is easier, and the contract can extend it. Backups must expire on a documented schedule |
| US (CCPA/CPRA and other state laws) | Deletion requests answered within 45 days (extendable once); service providers delete on the business's instruction                                                                                                                                                                                                                                      |
| Canada (PIPEDA, Quebec Law 25)      | Keep personal information only as long as necessary; destroy or anonymise afterwards                                                                                                                                                                                                                                                                     |
| All                                 | Legal hold and contract terms override schedules; most registry content is configuration, but `created_by` identifiers, user accounts and audit rows are personal data                                                                                                                                                                                   |

Data residency (EU, US, Canada): V2 is one deployment. Residency is solved by running separate regional deployments; an informational `organizations.region` is Later. Org admins request deletion; the platform admin executes it (V2).

## 8. Data model (Alembic revisions `0005`..`0012`)

```sql
CREATE TABLE organizations (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),          -- equals tenant_id everywhere
  slug          text NOT NULL UNIQUE CHECK (slug ~ '^[a-z0-9][a-z0-9-]{1,62}$'),
  name          text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 120),
  status        text NOT NULL DEFAULT 'active' CHECK (status IN ('active','suspended','pending_delete')),
  is_platform   boolean NOT NULL DEFAULT false,
  delete_after  timestamptz,
  legal_hold    boolean NOT NULL DEFAULT false,
  created_by    text NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  CHECK ((status = 'pending_delete') = (delete_after IS NOT NULL))
);
CREATE UNIQUE INDEX organizations_one_platform ON organizations (is_platform) WHERE is_platform;
CREATE FUNCTION platform_tenant_id() RETURNS uuid LANGUAGE sql STABLE
  AS $$ SELECT id FROM organizations WHERE is_platform $$;

CREATE TABLE products (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL REFERENCES organizations(id),
  slug text NOT NULL CHECK (slug ~ '^[a-z0-9][a-z0-9-]{1,62}$'),
  name text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 120),
  status text NOT NULL DEFAULT 'active' CHECK (status IN ('active','archived')),
  created_by text NOT NULL, created_at timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, slug), UNIQUE (id, tenant_id)
);

CREATE TABLE auth_configs (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id uuid NOT NULL REFERENCES organizations(id),
  product_id uuid,
  adapter text NOT NULL,
  config jsonb NOT NULL DEFAULT '{}',
  secret_enc bytea, key_id text,
  rev int NOT NULL DEFAULT 1,
  enabled boolean NOT NULL DEFAULT true,
  updated_by text NOT NULL, updated_at timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (product_id, tenant_id) REFERENCES products(id, tenant_id),
  UNIQUE NULLS NOT DISTINCT (tenant_id, product_id)
);

CREATE TABLE memberships (                                           -- user_id = Better Auth user id; no cross-schema foreign key
  user_id    text NOT NULL,
  tenant_id  uuid NOT NULL REFERENCES organizations(id),
  groups     text[] NOT NULL DEFAULT '{}' CHECK (cardinality(groups) <= 20),
  created_by text NOT NULL, created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (user_id, tenant_id)
);

CREATE TABLE platform_admins (
  user_id text PRIMARY KEY, granted_by text NOT NULL, granted_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE disabled_users (
  user_id text PRIMARY KEY, reason text NOT NULL DEFAULT '', disabled_by text NOT NULL, disabled_at timestamptz NOT NULL DEFAULT now()
);

-- revision 0009, after the Better Auth migration has created schema "auth":
CREATE VIEW auth_users AS SELECT id, username, email, name FROM auth."user";

CREATE TABLE registry_policies (
  registry_id uuid NOT NULL,
  tenant_id   uuid NOT NULL,
  action      text NOT NULL CHECK (action IN ('read','manage')),
  policy_id   uuid NOT NULL,
  PRIMARY KEY (registry_id, action, policy_id),
  FOREIGN KEY (registry_id, tenant_id) REFERENCES registry(id, tenant_id) ON DELETE CASCADE,
  FOREIGN KEY (policy_id, tenant_id) REFERENCES access_policies(id, tenant_id) ON DELETE RESTRICT
);
CREATE INDEX registry_policies_policy ON registry_policies (policy_id);

CREATE TABLE link_scope_rules (
  source_scope text NOT NULL CHECK (source_scope IN ('org','product','global')),
  target_scope text NOT NULL CHECK (target_scope IN ('org','product','global')),
  allowed boolean NOT NULL,
  PRIMARY KEY (source_scope, target_scope),
  CHECK (source_scope <> 'global' OR target_scope = 'global' OR NOT allowed)
);

CREATE TABLE admin_audit_log (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  actor text NOT NULL, action text NOT NULL, tenant_id uuid, target text,
  detail jsonb,                                                      -- never contains secrets
  at timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE access_policies ADD COLUMN kind text NOT NULL DEFAULT 'rule' CHECK (kind IN ('rule','open'));
ALTER TABLE registry
  ADD COLUMN scope text NOT NULL DEFAULT 'org' CHECK (scope IN ('org','product','global')),
  ADD COLUMN product_id uuid,
  ADD FOREIGN KEY (product_id, tenant_id) REFERENCES products(id, tenant_id),
  ADD CHECK ((scope = 'product') = (product_id IS NOT NULL));
-- trigger: setting scope = 'global' requires current_setting('app.platform_admin', true) = 'on'
-- after the data migration (4.4): DROP COLUMN visibility, DROP COLUMN policy_id
-- unique (tenant_id, type, slug) becomes UNIQUE NULLS NOT DISTINCT (tenant_id, product_id, type, slug)
```

Row-level security and grants:

- `products`, `auth_configs`, `registry_policies`: tenant isolation like every V1 tenant table. `memberships`: readable for own tenant **or** own `user_id`; writable for own tenant only (so org admins manage their own members under RLS).
- `organizations`, `platform_admins`, `disabled_users`, `link_scope_rules`: no tenant RLS; `krep_app` reads them, only `krep_platform` writes `organizations`, `platform_admins`, `disabled_users` and `admin_audit_log`.
- `krep_auth` owns the `auth` schema (Better Auth connects as it). `krep_app` gets `SELECT` on the `auth_users` view only; it cannot read credentials, accounts or sessions.
- The purge function runs as the owner role; the immutability trigger honours a purge-only session flag.
- Extra `SELECT` RLS rules for global content as in 4.3.
- Backend tests create a minimal stand-in `auth."user"` table so they run without Node.

### 9.4 V1 routes, extended

- `POST/PATCH /registry`: `scope` (`org` or `product` for org admins), `product` (slug), `policies: {"read": [ids], "manage": [ids]}` replace `visibility`/`policy_id`.
- `GET /registry`, `GET /registry/search`: filter `product`, `scope`; results carry `scope`.
- `POST /registry/{id}/links`: validates the scope pair (section 6).
- `/access-policies...`: unchanged; `open-to-all` is listed and read-only.

Errors added: `401 unauthenticated` (all selector/credential failures), `409 slug_taken`, `409 product_not_empty`, `409 org_legal_hold`, `422 auth_config_invalid`, `422 link_scope_not_allowed`, `403 scope_not_allowed`.

## 10. Admin panel UI

- **Stack:** Next.js (App Router) + TypeScript in `ui/`, shadcn/ui, TanStack Query, `react-querybuilder`, Better Auth. Next is UI + BFF + identity only (3.4): `/api/auth/*` and a pass-through `/api/v1/*` proxy; no registry or policy logic, no authorization decisions.
- **Pages:** `/login`, `/signup`, `/platform/...` (platform admins), `/org/[slug]/...` (org users; optional product picker).
- **Login:** username/password. After login the user picks an organisation (from `GET /me`) and optionally a product.
- **Platform console:** organisations (create wizard: details, first admin by username, auth, capabilities; suspend, delete schedule, legal hold, blockers), users (list, create, ban/unban, reset password, grant platform admin, delete orphans), global content, audit log.
- **Organisation console (org admin):** products, auth config (form from the adapter schema, test-a-token), members (add by username/email, groups), capability policies, policies (rule builder, live preview, test against a pasted token, history/restore), agents (list by scope; create/edit with only V1-required fields plus an Advanced JSON block; scope picker; read/manage policy multi-pickers; publish, archive, delete), links (including to global resources).
- **Rule builder:** `react-querybuilder` edits a tree; two converters map it to and from the V1 AST; the server stays authoritative through `POST /access-policies/preview`. We keep our own engine: policies are evaluated inside the search SQL, which an external engine (Casbin, OPA, Cerbos) cannot do. Needs a half-day spike first.

## 11. Security and operations

- Private by default: FastAPI admin/org routes and the Next app are internal; bind to localhost locally; every FastAPI route requires a credential. Sign-up is open by design (3.4) and needs Security review before any non-private exposure.
- Secrets and passwords: Fernet-encrypted org secrets; passwords exist only inside Better Auth; neither is returned or logged; log filters redact `secret`, `password`, `Authorization`, `Cookie`, `X-Platform-Key`.
- Least privilege: `krep_platform` is the only role that writes organisations, platform admins and the deny-list; `krep_auth` is confined to the `auth` schema; `krep_app` sees users only through `auth_users`.
- Login JWTs: verified through JWKS with `iss`/`aud`/`exp`; lifetime configurable (default 3600 s); `disabled_users` closes the revocation gap.
- Audit: every platform and org-admin write adds an `admin_audit_log` row without secret material.
- This changes authentication, secret handling and data deletion: Security and Legal review are needed before use beyond local development (not part of V2 build).

## 14. Acceptance tests (must pass)

Identity and roles:

1. A login JWT from the configured issuer is accepted; wrong issuer, wrong audience, expired, unknown key and `alg: none` return the identical `401`. (UI e2e: sign-up, username sign-in, JWT accepted by FastAPI.)
2. A user in organisations A and B selects either with `X-Org`; no membership gets `401`; changing groups or removing the membership applies on the next request; a user in `disabled_users` is blocked on the next request despite a valid JWT.
3. Selector mode with an organisation HMAC token: valid works; wrong secret, expired, `alg: none`, disallowed algorithm, wrong `aud`/`iss`, unknown or suspended organisation all return the identical `401`; an auth config cannot register the login issuer.
4. Product override: with `X-Product` selecting an overridden product only the product secret works; a product without override uses the organisation's; **without `X-Product` the request is organisation-level and sees no product-scoped resources.**
5. Secrets: no API response, log or audit row contains an organisation secret or password; the column holds ciphertext; key rotation keeps old secrets verifiable.
6. Platform routes accept only a platform admin (table or env key); org admins and org JWTs get `403`/`401`; with no env key and no platform admin the routes are closed.
7. An org admin can manage products, auth, members, policies, resources and links of their organisation and gets `404` for any other organisation; an org writer cannot manage products, auth or members; adding a member by an unknown username returns the generic `404`.
8. `krep_app` cannot write `organizations`, `platform_admins`, `disabled_users`, cannot read anything in `auth` except the `auth_users` view columns.

Access:

9. A resource with no `read` policy is invisible (`404`, absent from search) to others and visible to its creator and org admins.
10. Several `read` policies on one resource: allowed when any one is satisfied; removing the satisfied one hides it again immediately.
11. `open-to-all` at org scope reaches every product of that organisation and nobody in another; at product scope only callers of that product; at global scope every organisation, while a global resource with a restricted policy reaches only callers whose own token satisfies it.
12. Scope changes: `product`<->`org` by the owner's admin; `global` only by a platform admin (`403 scope_not_allowed` otherwise) on any organisation's published resource, with no data copy and an audit row; demoting a referenced global resource returns `409 resource_in_use`.
13. A tenant cannot write, archive or delete another organisation's global resource; the owner (or platform admin) can.
14. `manage` policies: a caller satisfying one (plus `registry-writers`) can edit another user's resource; a read-only caller cannot. Capability policies fail closed.

Links:

15. Allowed pairs work (org->org, org<->product, product->product same product, global->global, org->global, product->global); global->org, global->product and cross-product product->product return `422 link_scope_not_allowed`; an org agent linked to a global skill publishes with a frozen dependency, bundles for any caller of that organisation, is unaffected by later global versions, and blocks pruning (`409 version_in_use`) and deleting (`409 resource_in_use`) of the global skill version; `link_scope_rules` cannot be set to allow global->org.

Lifecycle:

16. Suspend blocks all organisation access at once; activate restores it. The purge job removes nothing before `delete_after`, nothing while `legal_hold` or while other organisations link to its global resources (blockers reported), and otherwise removes every row of the tenant (zero rows per table), nulls audit `detail`, and leaves other tenants untouched.

General:

17. V1 acceptance tests 1-28 still pass after the migration (updated only where `visibility` was used), and a migrated V1 tenant behaves as before.
18. A second fake organisation auth adapter in tests appears in the adapter listing and works end to end without core changes.
19. UI e2e (Playwright, local): two users sign up; the first is granted platform admin and creates an organisation with the other as first admin; that admin adds a product, a policy in the builder, an org-level and a product-level agent with policies, and a global skill link; a product-selected session sees both agents and an organisation-level session sees only the first.
