# Registry V1 — Implementation Spec

Status: ready for development. Design discussion history lives in `docs/registry/agents-table.md`; platform context in `v1-platform.md`.

## 0. How to read this spec

- **Must** = required for V1. **Later** = designed for, not built.
- Every section ends with the concrete examples a developer needs (SQL, request/response, test cases).
- Items marked **ASSUMPTION** were not explicitly decided; they are collected in section 17 for a quick yes/no.

## 1. Scope

The Registry is the catalogue of **agents** and **skills** that the platform loads lazily, on demand, per tenant and per caller.

In scope (V1):

1. Resource identity + immutable versions for two types: `agent`, `skill` (more types addable as data).
2. Discovery: full-text + fuzzy-name search with tenant synonyms (semantic/vector search is optional and off by default) that only ever returns resources the caller may see.
3. Access: named, editable, reusable policies. Rules are written over raw token/principal paths (AND / OR / NOT, nested), compiled to Postgres `jsonpath`, and evaluated in SQL.
4. Links between resources (agent <-> skill now, any pair later) with auto-load.
5. Version retention (latest 10 published), draft cap, configurable limits.
6. Multi-tenancy enforced by Postgres row-level security.

Out of scope (Later): runtime/execution, Tool Gateway, `tool` resource type, policy-referencing-policy, per-tenant limit overrides UI, notifications when a linked skill gets a new version, RAG/ingestion, direct browser authentication.

## 3. Concepts

| Term | Meaning |
| --- | --- |
| Resource | Stable identity row in `registry` (an agent or a skill). Has name, description, tags, visibility. |
| Version | Row in `registry_versions` holding one snapshot of the resource's spec. `draft` (editable) or `published` (immutable). |
| Subtype table | Per-type spec: `agents`, `skills`, keyed by version. |
| Current version | The published version that callers get by default (`registry.current_version_id`). |
| Policy | Named rule over token/principal paths; decides who can discover a `restricted` resource. Stored as an AST, compiled to a `jsonpath`. |
| Evaluation document | `{"token": <verified claims>, "principal": <optional trusted backend principal>}`; what policies are evaluated against. |
| Principal | The customer backend's description of the end user (`X-Principal`), honored only for trusted machine callers. |
| Link | Edge between two resources, e.g. agent `uses` skill. |
| Bundle | An agent version plus the skill versions it depends on, resolved for loading. |

## 4. Identity, tenancy and the evaluation document

We do not control the shape of customers' tokens (AWS Cognito, Okta, Entra ID, Auth0, Keycloak, Google and others differ in claim names, nesting, scalar-vs-array, and how much can be customised). So the registry never assumes claim names. Rules are written against the raw token (and an optional trusted principal), and only a few identity facts are resolved from per-issuer configuration.

### 4.1 Three ways a request is authenticated

| Mode | Credential | Tenant comes from | `token` in the evaluation document | `principal` honored? |
| --- | --- | --- | --- | --- |
| A. User JWT | `Authorization: Bearer <access token>` from a registered issuer | the issuer row (fixed tenant, or a claim path) | the verified claims | **never** (ignored if sent) |
| B. Machine JWT | Bearer token from OAuth2 client credentials, registered issuer | the issuer row | the verified claims (these describe the client, not a person) | yes, if the issuer has `allow_principal` |
| C. API key | `X-API-Key: <key>` | the key row | `{"api_key_id": "<id>"}` | yes, if the key has `allow_principal` |

We accept the **access token** (audience = our API). Access tokens can be thin (for example, Cognito access tokens do not carry email; user attributes live in the ID token). Rules that need richer attributes use the principal (below). Calling the issuer's `/userinfo` to enrich is Later.

### 4.2 What a principal is

A **principal** is the customer's own description of the end user, asserted by the customer's backend. It is not a token feature, so no identity provider has to support it. It matches `v1-platform.md` section 3 ("the authenticated customer backend is trusted to provide the principal").

It is sent in the header `X-Principal` as base64url-encoded JSON (object, at most 4 KB). Free-form except `id` (string, required):

```json
{ "id": "user-123", "roles": ["support"], "department": "billing", "clearance": 3 }
```

The registry does not verify a principal; it trusts it only because the caller authenticated as a backend that is allowed to assert one (`allow_principal`). A user token that sends `X-Principal` is ignored, otherwise end users could forge it.

Worked scenarios:

1. **SPA calls with the user's token (mode A), issuer Entra ID.** Evaluation document: `{"token": {"tid": "...", "oid": "...", "roles": ["Billing.Lead"]}}`. Rule: `"Billing.Lead" in token.roles`.
2. **Customer backend, Cognito client-credentials token (mode B).** The token only says who the *client* is: `{"sub": "client-abc", "client_id": "client-abc", "scope": "registry/read"}`. The backend adds `X-Principal: {"id": "user-123", "roles": ["support"]}`. Rule: `"support" in principal.roles`.
3. **Customer backend, API key (mode C).** `token` is just the key id; everything about the user comes from the principal. Same rule as 2.
4. **A customer with several IdPs.** Each issuer is a separate `token_issuers` row. Rules can combine paths (`"admin" in token.groups || "admin" in token["cognito:groups"]`) or the customer's backend can normalise everything into a principal.

### 4.3 Evaluation document, variables and resolved identity

Every rule is evaluated against one JSON document and a small set of variables:

```json
{ "token": { "...verified claims or {api_key_id}..." }, "principal": { "...or {} when absent..." } }
```

Variables: `var.tenant_id` (the resolved tenant). A missing root is `{}`, so rules over it simply do not match.

Per request the service resolves:

```json
{ "tenant_id": "6f1d2c6e-0000-4000-8000-0000000000a1", "user_id": "u42",
  "doc": { "token": { "...": "..." }, "principal": { } },
  "can_write": true, "can_admin": false }
```

- **Tenant:** from `token_issuers` (`tenant_id` fixed for that issuer, or read from `tenant_claim_path`) or from `api_keys.tenant_id`. Never from the request body.
- **User id (used for `private` visibility and ownership):** the principal's `id` when a principal is honored (missing `id` -> `400 principal_id_required`); otherwise the value at the issuer's `user_claim_path` (default `["sub"]`); a machine token without a principal gets `client:<sub>`.
- **Write/admin rights:** two **reserved policies per tenant**, named `registry-admins` and `registry-writers`, evaluated by the same engine against the same document. `can_admin` = `registry-admins` satisfied; `can_write` = `can_admin` or `registry-writers` satisfied. A missing or unsatisfied policy means nobody (fail closed). Every authenticated caller can read (discovery), subject to visibility.
- Reserved policies cannot be deleted or renamed. They are created by an ops command at onboarding and recovered by the same command if an admin locks themselves out:

```bash
uv run krep tenant init --tenant <tenant_id> --admin-rule 'token.groups == "grc-admins"' --writer-rule 'token.groups == "grc-editors"'
uv run krep policy reset registry-admins --tenant <tenant_id> --rule 'token.groups == "grc-admins"'
```

| Permission | Allows |
| --- | --- |
| read (any authenticated caller) | discovery, read visible resources, bundles |
| `can_write` | create/edit/publish/delete **own** resources and drafts, create links ("own" = `created_by = user_id`) |
| `can_admin` | everything in `can_write` on **any** resource in the tenant, manage policies, accept/reject links on any resource |

`token_issuers` and `api_keys` are global, ops-managed tables read **before** the tenant is known, so they are exempt from RLS and read-only for the application role (5.4).

### 4.4 Row-level security (Must)

Every tenant table has `tenant_id uuid NOT NULL`, `ENABLE` and `FORCE ROW LEVEL SECURITY`, and this policy:

```sql
CREATE POLICY tenant_isolation ON registry
  USING (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (tenant_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
```

The service opens every transaction with:

```sql
SELECT set_config('app.tenant_id', :tenant_id, true);   -- true = local to the transaction
```

The application connects as a role that is **not** a superuser and does **not** have `BYPASSRLS`. If `app.tenant_id` is unset, the policy evaluates to NULL and no rows are visible (fail closed). The `NULLIF(..., '')` matters: after a transaction that used `set_config(..., true)`, a pooled connection reports the setting as an empty string rather than NULL, and a bare `''::uuid` would raise an error instead of returning no rows (found while testing this spec). Global tables without `tenant_id`: `registry_types`, `link_rules`, global rows of `resource_limits`.

Cross-tenant check (required test): with `app.tenant_id = A`, `SELECT * FROM registry WHERE tenant_id = B` returns zero rows.

## 5. Data model (DDL)

This block is the content of Alembic revision `0001_registry_schema` (see 5.4). All timestamps are `timestamptz`; ids are `uuid DEFAULT gen_random_uuid()`.

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE FUNCTION immutable_array_to_string(text[], text) RETURNS text
  LANGUAGE sql IMMUTABLE PARALLEL SAFE AS $$ SELECT array_to_string($1, $2) $$;

-- ---------- types ----------
CREATE TABLE registry_types (
  type          text PRIMARY KEY CHECK (type ~ '^[a-z][a-z0-9_]{1,31}$'),
  subtype_table text NOT NULL,
  description   text NOT NULL DEFAULT ''
);

-- ---------- policies (declared first: registry references it) ----------
CREATE TABLE access_policies (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id        uuid NOT NULL,
  name             text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 120),
  description      text NOT NULL DEFAULT '' CHECK (char_length(description) <= 1000),
  ast              jsonb NOT NULL,                  -- canonical rule tree; source of truth
  source           text  NOT NULL,                  -- rule text, regenerated from ast
  compiled_path    jsonpath NOT NULL,               -- derived by the compiler (8.3)
  compiler_version smallint NOT NULL,
  reserved         boolean NOT NULL DEFAULT false,  -- registry-admins / registry-writers
  rev              int  NOT NULL DEFAULT 1,
  created_by       text NOT NULL,
  created_at       timestamptz NOT NULL DEFAULT now(),
  updated_by       text NOT NULL,
  updated_at       timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, name),
  UNIQUE (id, tenant_id)
);
CREATE INDEX access_policies_tenant ON access_policies (tenant_id);

CREATE TABLE access_policy_history (
  policy_id  uuid NOT NULL REFERENCES access_policies(id) ON DELETE CASCADE,
  tenant_id  uuid NOT NULL,
  rev        int  NOT NULL,
  ast        jsonb NOT NULL,
  source     text  NOT NULL,
  changed_by text NOT NULL,
  changed_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (policy_id, rev)
);

-- ---------- registry identity ----------
CREATE TABLE registry (
  id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id          uuid NOT NULL,
  type               text NOT NULL REFERENCES registry_types(type),
  slug               text NOT NULL CHECK (slug ~ '^[a-z0-9][a-z0-9-]{1,62}$'),
  name               text NOT NULL CHECK (char_length(name) BETWEEN 1 AND 120),
  description        text NOT NULL DEFAULT '' CHECK (char_length(description) <= 2000),
  tags               text[] NOT NULL DEFAULT '{}' CHECK (cardinality(tags) <= 20),
  visibility         text NOT NULL DEFAULT 'private'
                     CHECK (visibility IN ('private','tenant','restricted')),
  policy_id          uuid,
  status             text NOT NULL DEFAULT 'draft'
                     CHECK (status IN ('draft','published','archived')),
  current_version_id uuid,
  next_version       int  NOT NULL DEFAULT 1,
  search_tsv         tsvector GENERATED ALWAYS AS (
                       setweight(to_tsvector('english', coalesce(name,'')), 'A') ||
                       setweight(to_tsvector('english', coalesce(description,'')), 'B') ||
                       setweight(to_tsvector('english', immutable_array_to_string(tags,' ')), 'C')
                     ) STORED,
  meta               jsonb NOT NULL DEFAULT '{}' CHECK (pg_column_size(meta) <= 16384),
  created_at         timestamptz NOT NULL DEFAULT now(),
  created_by         text NOT NULL,
  updated_at         timestamptz NOT NULL DEFAULT now(),
  updated_by         text NOT NULL,
  UNIQUE (tenant_id, type, slug),
  UNIQUE (id, type),
  UNIQUE (id, tenant_id),
  FOREIGN KEY (policy_id, tenant_id) REFERENCES access_policies(id, tenant_id) ON DELETE RESTRICT,
  CHECK (visibility <> 'restricted' OR policy_id IS NOT NULL)
);

CREATE INDEX registry_tenant_type_status ON registry (tenant_id, type, status);
CREATE INDEX registry_tags_gin  ON registry USING gin (tags);
CREATE INDEX registry_tsv_gin   ON registry USING gin (search_tsv);
CREATE INDEX registry_name_trgm ON registry USING gin (name gin_trgm_ops);

-- ---------- versions ----------
CREATE TABLE registry_versions (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  registry_id  uuid NOT NULL REFERENCES registry(id) ON DELETE CASCADE,
  tenant_id    uuid NOT NULL,
  version      int  NOT NULL,
  status       text NOT NULL DEFAULT 'draft' CHECK (status IN ('draft','published')),
  content_hash text,                              -- sha256 hex, set at publish
  created_by   text NOT NULL,
  created_at   timestamptz NOT NULL DEFAULT now(),
  published_at timestamptz,
  UNIQUE (registry_id, version),
  UNIQUE (id, registry_id),
  CHECK ((status = 'published') = (published_at IS NOT NULL AND content_hash IS NOT NULL))
);
CREATE INDEX registry_versions_drafts ON registry_versions (tenant_id) WHERE status = 'draft';

ALTER TABLE registry
  ADD FOREIGN KEY (current_version_id) REFERENCES registry_versions(id)
  ON DELETE RESTRICT DEFERRABLE INITIALLY DEFERRED;

-- ---------- subtype tables (one per type) ----------
CREATE TABLE agents (
  version_id     uuid PRIMARY KEY,
  registry_id    uuid NOT NULL,
  tenant_id      uuid NOT NULL,
  type           text NOT NULL DEFAULT 'agent' CHECK (type = 'agent'),
  model          text NOT NULL,
  model_config   jsonb NOT NULL DEFAULT '{}',
  system_prompt  text  NOT NULL,
  input_schema   jsonb NOT NULL DEFAULT '{}',
  output_schema  jsonb NOT NULL DEFAULT '{}',
  hitl_rules     jsonb NOT NULL DEFAULT '[]',
  runtime_config jsonb NOT NULL DEFAULT '{}',
  tool_refs      jsonb NOT NULL DEFAULT '[]',     -- placeholder until `tool` type exists
  FOREIGN KEY (version_id, registry_id) REFERENCES registry_versions(id, registry_id) ON DELETE CASCADE,
  FOREIGN KEY (registry_id, type) REFERENCES registry(id, type) ON DELETE CASCADE
);

CREATE TABLE skills (
  version_id   uuid PRIMARY KEY,
  registry_id  uuid NOT NULL,
  tenant_id    uuid NOT NULL,
  type         text NOT NULL DEFAULT 'skill' CHECK (type = 'skill'),
  instructions text  NOT NULL,
  resources    jsonb NOT NULL DEFAULT '[]',
  FOREIGN KEY (version_id, registry_id) REFERENCES registry_versions(id, registry_id) ON DELETE CASCADE,
  FOREIGN KEY (registry_id, type) REFERENCES registry(id, type) ON DELETE CASCADE
);

-- ---------- links ----------
CREATE TABLE link_rules (
  source_type       text NOT NULL REFERENCES registry_types(type),
  target_type       text NOT NULL REFERENCES registry_types(type),
  relation          text NOT NULL,
  auto_load_allowed boolean NOT NULL DEFAULT false,
  accept_by         text NOT NULL CHECK (accept_by IN ('source','target')),
  PRIMARY KEY (source_type, target_type, relation)
);

CREATE TABLE registry_links (
  id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id         uuid NOT NULL,
  source_id         uuid NOT NULL REFERENCES registry(id) ON DELETE CASCADE,
  target_id         uuid NOT NULL REFERENCES registry(id) ON DELETE RESTRICT,
  relation          text NOT NULL,
  pinned_version_id uuid REFERENCES registry_versions(id) ON DELETE RESTRICT,
  auto_load         boolean NOT NULL DEFAULT false,
  origin_id         uuid NOT NULL,                 -- source_id or target_id: who initiated
  status            text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','accepted','rejected')),
  created_by        text NOT NULL,
  created_at        timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, source_id, target_id, relation),
  CHECK (source_id <> target_id),
  CHECK (origin_id IN (source_id, target_id))
);
CREATE INDEX registry_links_src ON registry_links (tenant_id, source_id, relation);
CREATE INDEX registry_links_tgt ON registry_links (tenant_id, target_id, relation);

CREATE TABLE registry_version_deps (            -- frozen when the source version is published
  version_id            uuid NOT NULL REFERENCES registry_versions(id) ON DELETE CASCADE,
  depends_on_version_id uuid NOT NULL REFERENCES registry_versions(id) ON DELETE RESTRICT,
  tenant_id             uuid NOT NULL,
  relation              text NOT NULL,
  auto_load             boolean NOT NULL,
  PRIMARY KEY (version_id, depends_on_version_id, relation)
);
CREATE INDEX registry_version_deps_rev ON registry_version_deps (depends_on_version_id);

-- ---------- limits ----------
CREATE TABLE resource_limits (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  scope_type    text NOT NULL CHECK (scope_type IN ('global','tenant','org','product')),
  scope_id      text,
  resource_type text REFERENCES registry_types(type),
  limit_key     text NOT NULL,
  value         int  NOT NULL CHECK (value >= 0),
  CHECK ((scope_type = 'global') = (scope_id IS NULL)),
  UNIQUE NULLS NOT DISTINCT (scope_type, scope_id, resource_type, limit_key)
);

-- ---------- search synonyms (tenant-curated, query-side; see 9.4) ----------
CREATE TABLE search_synonyms (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id  uuid NOT NULL,
  terms      text[] NOT NULL CHECK (cardinality(terms) BETWEEN 2 AND 10),
  created_by text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX search_synonyms_tenant ON search_synonyms (tenant_id);

-- ---------- identity (global, ops-managed, read before the tenant is known: no RLS) ----------
CREATE TABLE token_issuers (
  issuer            text PRIMARY KEY,
  audience          text NOT NULL,
  jwks_uri          text NOT NULL CHECK (left(jwks_uri, 8) = 'https://'),
  tenant_id         uuid,                          -- fixed tenant for this issuer, or
  tenant_claim_path text[],                        -- path segments of the claim holding the tenant id
  user_claim_path   text[] NOT NULL DEFAULT '{sub}',
  allow_principal   boolean NOT NULL DEFAULT false,  -- true only for trusted backend (machine) issuers
  enabled           boolean NOT NULL DEFAULT true,
  CHECK ((tenant_id IS NOT NULL) <> (tenant_claim_path IS NOT NULL))
);

CREATE TABLE api_keys (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id       uuid NOT NULL,
  name            text NOT NULL,
  key_hash        bytea NOT NULL UNIQUE,           -- sha256 of the key; the key is shown once
  allow_principal boolean NOT NULL DEFAULT false,
  created_at      timestamptz NOT NULL DEFAULT now(),
  revoked_at      timestamptz
);
```

### 5.1 Immutability trigger (Must; Alembic revision `0002_integrity_triggers`)

Published versions and their subtype rows can never be updated; only deleted (by prune/delete rules).

```sql
CREATE FUNCTION reject_published_update() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF TG_TABLE_NAME = 'registry_versions' THEN
    IF OLD.status = 'published' THEN
      RAISE EXCEPTION USING ERRCODE = '23514', MESSAGE = 'published version ' || OLD.id || ' is immutable';
    END IF;
  ELSIF (SELECT status FROM registry_versions WHERE id = OLD.version_id) = 'published' THEN
    RAISE EXCEPTION USING ERRCODE = '23514', MESSAGE = 'published version ' || OLD.version_id || ' is immutable';
  END IF;
  RETURN NEW;
END $$;

CREATE TRIGGER registry_versions_immutable BEFORE UPDATE ON registry_versions
  FOR EACH ROW EXECUTE FUNCTION reject_published_update();
CREATE TRIGGER agents_immutable BEFORE UPDATE ON agents
  FOR EACH ROW EXECUTE FUNCTION reject_published_update();
CREATE TRIGGER skills_immutable BEFORE UPDATE ON skills
  FOR EACH ROW EXECUTE FUNCTION reject_published_update();
```

Publishing is the one allowed transition (`draft -> published`): the publish transaction sets status, `published_at` and `content_hash` in a single UPDATE of a **draft** row (the trigger only blocks rows that are *already* published).

### 5.4 Migrations with Alembic, roles and grants

Rules:

- One Alembic revision per file (section 2 layout). Revisions execute SQL with `op.get_bind().exec_driver_sql(...)`: no SQLAlchemy models, no autogenerate, and no bind-parameter parsing of `:` inside SQL. The psycopg driver still treats `%` as a placeholder marker even without parameters, so migration SQL must not contain a bare `%` (use `left()`/`starts_with()` instead of `LIKE 'x%'`, or write `%%`).
- Revision content: `0001` = the DDL block of section 5 (its `CREATE EXTENSION IF NOT EXISTS` lines are no-ops locally because the init script already created them; on managed Postgres a privileged role must create the extensions once: verified that a non-superuser database owner can create both `pg_trgm` and `pgcrypto`; `vector` (only needed if semantic search is enabled, 7.6) cannot be created that way and needs a superuser locally or the provider's privileged role such as `rds_superuser` on AWS; roles and their passwords are provisioned outside Alembic, by the local init script or infrastructure code, because secrets do not belong in migration files); `0002` = 5.1; `0003` = RLS and grants (below); `0004` = 5.2.
- `downgrade()` drops in reverse order: delete seed rows; drop policies and revoke; drop triggers and the trigger function; drop tables in reverse dependency order and the helper function. It never drops extensions.
- `env.py` reads `KREP_MIGRATION_DATABASE_URL` (`postgresql+psycopg://...`), sets `target_metadata = None`, and runs online only.
- Never edit a merged revision; add a new one. Example: enabling semantic search is a new revision that adds the embedding column (7.6).

## 7. Resource and version lifecycle

### 7.1 States

```text
resource.status:   draft --(first publish)--> published --(archive)--> archived --(unarchive)--> published
version.status:    draft --(publish)--> published          (published rows are immutable)
```

- `registry.status = 'published'` iff `current_version_id IS NOT NULL`.
- Only `published` resources appear in discovery. Drafts are visible via the management list to their owner/admins.
- `archived`: hidden from discovery, cannot receive new links, existing frozen dependencies keep resolving.

### 7.2 Create resource (creates version 1 as a draft)

`POST /v1/registry`

```json
{
  "type": "agent",
  "slug": "refund-assistant",
  "name": "Refund Assistant",
  "description": "Handles refund requests up to 500 USD and escalates the rest.",
  "tags": ["billing", "refunds"],
  "visibility": "private",
  "spec": { "model": "claude-sonnet-5-5", "system_prompt": "You are a refund assistant..." }
}
```

`201`:

```json
{
  "id": "0b8f6d9a-3c11-4b52-9d0a-7a1e2f4c5d10",
  "type": "agent", "slug": "refund-assistant", "status": "draft",
  "visibility": "private", "current_version": null,
  "version": { "version": 1, "status": "draft" }
}
```

Steps (one transaction): check `max_drafts` (7.5) -> insert `registry` (`next_version = 2`) -> insert `registry_versions` (version 1, draft) -> insert subtype row (validated against the type's schema).

Errors: `409 slug_taken`, `422 validation_failed` (field-level list), `409 draft_limit_reached`.

### 7.3 Draft versions

- `POST /v1/registry/{id}/versions` creates the next draft (`version = next_version`, then increment). Body may include `{"from_version": 3}` to copy that version's spec; otherwise the current version's spec is copied; for a never-published resource the latest draft is copied.
- `PUT /v1/registry/{id}/versions/{n}` replaces a draft's spec. `409 version_immutable` if it is published.
- `DELETE /v1/registry/{id}/versions/{n}` deletes a draft freely, or a published version under the rules in 7.4.
- Drafts count toward `max_drafts`.

### 7.4 Publish and retention (Must)

`POST /v1/registry/{id}/versions/{n}/publish`

One transaction:

1. Lock the resource row (`SELECT ... FOR UPDATE`).
2. Verify version `n` is a draft; validate spec; compute `content_hash`.
3. Count published versions of this resource. If `count >= max_published_versions` (10): choose the **oldest published version that is not the current version** and `DELETE` it. If the delete raises a foreign-key violation (restrict), abort and return `409 version_in_use` with the referrers (example below). Nothing else changes.
4. Resolve this version's links into `registry_version_deps` (7.8).
5. `UPDATE` the draft to `published` (status, `published_at`, `content_hash`).
6. Set `registry.current_version_id = n` (only if publishing is "make current", the default; body `{"make_current": false}` leaves current unchanged), set `registry.status = 'published'`.

`409 version_in_use` example (publishing v11 while v1 is pinned):

```json
{
  "error": "version_in_use",
  "message": "Publishing v11 requires archiving the oldest version (v1), but it is still referenced. De-reference it first.",
  "version_to_remove": 1,
  "referenced_by": [
    { "kind": "link_pin", "resource": "support-bot", "resource_id": "c2a1...", "link_id": "e19b..." },
    { "kind": "version_dep", "resource": "billing-agent", "version": 7 },
    { "kind": "active_run", "run_id": "r_123" }
  ]
}
```

- Referrers are discovered via the restrict violation, then enumerated by querying `registry_links.pinned_version_id`, `registry_version_deps.depends_on_version_id`, and (when the runs table exists) active runs through one function `version_in_use(version_id)` that V1 implements for links and deps and leaves a hook for runs.
- UI shows the warning before publishing the 11th: "Your oldest version (v1) will be permanently deleted."
- Deleting a *published* version manually follows the same restrict rules; deleting the current version is rejected (`409 version_is_current`; repoint first).

**Repoint current (rollback):** `POST /v1/registry/{id}/current` with `{"version": 6}`; version must be published and retained.

### 7.5 Limits

Every limit goes through one function; no code reads `resource_limits` any other way.

```sql
-- get_limit(tenant, product, org, resource_type, key)
SELECT value FROM resource_limits
WHERE limit_key = :key
  AND (resource_type IS NULL OR resource_type = :type)
  AND ( (scope_type = 'product' AND scope_id = :product)
     OR (scope_type = 'org'     AND scope_id = :org)
     OR (scope_type = 'tenant'  AND scope_id = :tenant)
     OR  scope_type = 'global')
ORDER BY CASE scope_type WHEN 'product' THEN 1 WHEN 'org' THEN 2 WHEN 'tenant' THEN 3 ELSE 4 END,
         (resource_type IS NULL)
LIMIT 1;
```

Most specific wins; a type-specific row beats a type-agnostic row at the same scope. V1 only has `global` rows, so this always returns the seed values; adding `INSERT INTO resource_limits VALUES ('tenant','t1','agent','max_drafts',200)` later changes behaviour with no code change.

**Draft cap enforcement** (a CHECK cannot count rows): in the create/new-draft transaction,

```sql
SELECT pg_advisory_xact_lock(hashtextextended(:tenant_id || ':' || :type, 0));
SELECT count(*) FROM registry_versions v JOIN registry r ON r.id = v.registry_id
 WHERE v.tenant_id = :tenant_id AND r.type = :type AND v.status = 'draft';
```

If `count >= get_limit(..., 'max_drafts')` return `409 draft_limit_reached` with `{limit: 50, current: 50}`. Limits are read-only via `GET /v1/limits` in V1 (returns the effective values for the caller's tenant).

### 7.6 Semantic search (optional, **off by default**)

V1 ships **without embeddings**: no pgvector, no embedding provider, no vector column. Search is full-text plus fuzzy name matching plus tenant synonyms (section 9). Config flag `SEARCH_SEMANTIC_ENABLED=false`.

The code keeps a seam for later: a small provider interface (`embed_documents(texts)`, `embed_query(text)`, `dimension`, `model_name`) that V1 does not implement. When semantic search is wanted:

1. **Evaluate first.** Build 30-50 labelled queries (query -> the resource that should be found) and compare recall@10 of lexical+fuzzy against lexical+fuzzy+semantic on real data. Choose the model and dimension only then. (A free local model such as `fastembed` with `bge-small` is enough for development; a hosted model goes through the approved route.)
2. **Privileged step:** a superuser (or `rds_superuser` on AWS) runs `CREATE EXTENSION vector`.
3. **New Alembic revision:** `ALTER TABLE registry ADD COLUMN embedding vector(N), ADD COLUMN embedding_model text;` plus an optional HNSW index once a tenant's visible set exceeds about 50k rows.
4. **Backfill job** embeds `name + "\n" + description + "\n" + tags joined by space` for all rows; the write path embeds on create and whenever name/description/tags change. A provider failure leaves `embedding = NULL` and a retry job fills it later.
5. **Search:** add `embedding` to the `visible` CTE and a third branch merged by RRF; a provider failure at query time skips that branch and the response carries `"degraded": true`.

```sql
, sem AS (
  SELECT id, row_number() OVER (ORDER BY embedding <=> :qvec) AS rnk
  FROM visible WHERE embedding IS NOT NULL
  ORDER BY embedding <=> :qvec LIMIT 50
)
-- score = COALESCE(1.0/(60+lex.rnk),0) + COALESCE(1.0/(60+fuzzy.rnk),0) + COALESCE(1.0/(60+sem.rnk),0)
```

Changing the model or dimension later is another revision plus a re-embed; `embedding_model` shows which rows are stale.

### 7.7 Archive / delete resource

- `POST /v1/registry/{id}/archive` and `/unarchive`.
- `DELETE /v1/registry/{id}`: succeeds only when no resource links to it as a target and no version of it is referenced (restrict FKs); its own outgoing links and versions cascade. Otherwise `409 resource_in_use` with referrers. Archive is the soft path.

### 7.8 Links, acceptance and auto-load

Create: `POST /v1/registry/{id}/links`

```json
{ "other_id": "5d7e...-skill-id", "relation": "uses", "direction": "out", "pinned_version": null, "auto_load": true }
```

`direction: "out"` means `{id}` is the source (agent uses skill); `"in"` means `{id}` is the target (skill attaches itself to agent `other_id`).

Rules:

1. `(source_type, target_type, relation)` must exist in `link_rules`, else `422 link_not_allowed`. `auto_load` can only be true if `auto_load_allowed`.
2. Both resources must be in the same tenant and not archived. Creator must have `can_write` (4.3) on the resource they are creating the link from.
3. **Acceptance:** `link_rules.accept_by` names the side whose behaviour changes (for agent `uses` skill: the `source`, the agent). If the creator can edit that side's resource (owns it, or is admin) the link is created `accepted`. Otherwise it is `pending` until the owner/admin of that side calls `POST /v1/links/{id}/accept` (or `/reject`). Only `accepted` links participate in auto-load and dependency freezing.
4. **No cycles:** before insert, a recursive query checks that `target` cannot already reach `source` through accepted links of any relation; if it can, `422 link_cycle`.
5. `pinned_version`: NULL means "follow the target's current version at the time the source version is published"; a number pins that published version of the target.

Example: skill owner Priya attaches her skill to Ravi's agent.

```text
POST /v1/registry/{skill-id}/links  {"other_id":"{agent-id}","relation":"uses","direction":"in","auto_load":true}
-> 201 {"status":"pending", "accept_by":"source", "waiting_on":"owner of refund-assistant"}
Ravi: POST /v1/links/{link-id}/accept  -> {"status":"accepted"}
```

**Freezing at publish.** When an agent version is published, for every accepted outgoing link the service writes one `registry_version_deps` row: `depends_on_version_id` = pinned version, or the target's `current_version_id` when unpinned. Example: agent v7 published while `refund-policy` skill's current is v4 -> deps row `(agent v7 -> skill v4, uses, auto_load=true)`. If the target has no published version, publish fails `422 dependency_unpublished` naming it.

After this, the published agent v7 always loads skill v4, even if the skill later publishes v5 (the agent must be republished to adopt v5).

**Lookups from either side (symmetric):**

```sql
-- skills used by agent X
SELECT * FROM registry_links WHERE tenant_id=:t AND source_id=:x AND status='accepted';
-- agents using skill Y
SELECT * FROM registry_links WHERE tenant_id=:t AND target_id=:y AND status='accepted';
```

API: `GET /v1/registry/{id}/links?direction=out|in|both&status=accepted`.

### 7.9 Bundle resolution (lazy load)

`GET /v1/registry/{id}/bundle?version=7` (version omitted = current). Returns the agent version spec plus every dependency with `auto_load = true`, recursively, depth limit 5.

```sql
WITH RECURSIVE bundle AS (
  SELECT d.depends_on_version_id AS vid, d.relation, 1 AS depth
  FROM registry_version_deps d WHERE d.version_id = :root_version AND d.auto_load
  UNION
  SELECT d.depends_on_version_id, d.relation, b.depth + 1
  FROM bundle b JOIN registry_version_deps d ON d.version_id = b.vid
  WHERE d.auto_load AND b.depth < 5
)
SELECT vid, relation, depth FROM bundle;
```

Response:

```json
{
  "root": { "id": "0b8f...", "type": "agent", "version": 7, "spec": { "...": "..." } },
  "dependencies": [
    { "id": "5d7e...", "type": "skill", "slug": "refund-policy", "version": 4, "relation": "uses", "spec": { "...": "..." } }
  ]
}
```

For a **draft** root version there are no frozen deps; the service resolves live accepted links instead (same shape) so authors can preview. The caller must be allowed to see the root (section 8); dependencies are included because the owner of the agent accepted them, regardless of the caller's discovery rights for the skill (the agent's publisher vouched for the link).

## 8. Discovery and access policies

### 8.1 Visibility

| `visibility` | Who can discover (published resources only) |
| --- | --- |
| `private` | the creator (`created_by = user_id`, resolved per 4.3) |
| `tenant` | any authenticated caller in the tenant |
| `restricted` | callers whose evaluation document satisfies the resource's policy (8.4) |

Discovery (search, get-by-id, bundle) applies the predicate. Management endpoints (`GET /v1/registry`, edit, publish) use ownership/admin permission instead and also show drafts. A resource the caller cannot see returns **404**, never 403, so existence does not leak. Result counts only count visible rows.

### 8.2 Rule language

Users write rules over raw token (and principal) paths. The same rule can be authored as text or in the visual builder; both produce the same AST (8.3), and text shown in the UI is always regenerated from the AST (canonical formatting).

```text
expr    := or
or      := and ("||" and)*
and     := unary ("&&" unary)*
unary   := "!" unary | "(" expr ")" | cmp
cmp     := operand ("==" | "!=" | "<" | "<=" | ">" | ">=") literal
         | literal "in" operand                              // "admin" in token.roles
         | operand "in" "[" literal ("," literal)* "]"       // token.org.region in ["emea","apac"]
         | operand "." ("startsWith" | "endsWith") "(" string ")"
         | "has" "(" operand ")"
operand := ("token" | "principal") ( "." ident | "[" string "]" )*
literal := string | number | "true" | "false" | "null" | "var" "." "tenant_id"
ident   := [A-Za-z_][A-Za-z0-9_]*
```

Precedence: `!` > `&&` > `||`. Strings are double-quoted with JSON escapes; numbers are JSON numbers. Use `token["https://acme.com/roles"]` for keys that are not identifiers. No comments, no regex, no arithmetic, no comparison between two paths in V1.

Semantics (shown in the UI next to the editor, and documented for customers):

- **Lax and existential.** `token.roles == "admin"` is true if the claim is the string `admin` **or** an array containing it, because identity providers are inconsistent about scalar vs array. `"admin" in token.roles` is the same test, written the other way.
- **`!=` means "no element equals".** `token.roles != "admin"` is true when the claim is missing or contains no `admin`.
- **No type coercion.** `token.clearance >= 3` is false when the claim is the string `"3"`.
- **Missing claim = false**, so `!(...)` over a missing claim is true. Use `has()` to require presence.
- Runtime errors evaluate as "not satisfied" (fail closed).
- Group overage (for example Entra omitting `groups` when a user has too many) looks like a missing claim; rules over it do not match. The test tool warns (8.6). Documented workarounds: app roles, or a backend-supplied principal.

Limits: max 100 AST nodes, depth 8, at most 8 path segments, string literals <= 256 chars, `in [...]` lists <= 50 values. Over limit: `422 policy_too_large`.

### 8.3 AST and compiler (`policy/compile.py`)

**AST** (canonical, stored in `access_policies.ast`; the UI builder edits this):

```json
{"op":"and","args":[
  {"op":"cmp","path":{"root":"token","segments":["department"]},"cmp":"==","value":{"lit":"billing"}},
  {"op":"or","args":[
    {"op":"member","path":{"root":"token","segments":["roles"]},"value":{"lit":"manager"}},
    {"op":"member","path":{"root":"token","segments":["roles"]},"value":{"lit":"support-lead"}}]},
  {"op":"not","arg":
    {"op":"member","path":{"root":"token","segments":["groups"]},"value":{"lit":"contractors"}}}]}
```

Node ops: `and`/`or` (`args`, at least 1), `not` (`arg`), `cmp` (`==`,`!=`,`<`,`<=`,`>`,`>=`), `member` (value `in` path), `in_list` (`values`), `starts_with`, `ends_with`, `has`. A value is `{"lit": <string|number|bool|null>}` or `{"var": "tenant_id"}`.

**Compilation** produces a single `jsonpath` string, stored in `access_policies.compiled_path`, evaluated by `jsonb_path_match(doc, compiled_path, vars, true)`:

| Node | Compiles to |
| --- | --- |
| `cmp ==`, `member` | `exists(<path>[*] ? (@ == <value>))` |
| `cmp !=` | `!(exists(<path>[*] ? (@ == <value>)))` |
| `cmp < <= > >=` | `exists(<path>[*] ? (@ >= <value>))` |
| `in_list` | `exists(<path>[*] ? (@ == v1 \|\| @ == v2 ...))` |
| `starts_with` | `exists(<path>[*] ? (@ starts with "<s>"))` |
| `ends_with` | `exists(<path>[*] ? (@ like_regex "<regex-escaped s>$"))` |
| `has` | `exists(<path>)` |
| `and` / `or` | children joined with ` && ` / ` \|\| `; a child that is itself `and`/`or` is parenthesised |
| `not` | `!(<child>)` |

`<path>` = `$` followed by `."segment"` for the root and every segment, **always quoted** (so keys with dots, slashes or colons just work), e.g. `$."token"."org"."region"`. `<value>` is a JSON-escaped literal, or `$tenant_id` for `var.tenant_id` (passed through the jsonpath `vars` argument).

Every comparison is wrapped in `exists(... ? (...))` on purpose: it always yields a definite true/false, so `&&`, `||` and `!` behave as ordinary two-valued logic even when a claim is missing or has the wrong type.

**Safety rules (Must):**

1. The compiler walks the validated AST only; user text is never concatenated into SQL.
2. String literals are JSON-escaped; `ends_with` first regex-escapes the literal (`\ . [ ] { } ( ) * + ? ^ $ |`), then JSON-escapes the result.
3. Path segments: 1-128 chars, no control characters (`< 0x20`, `0x7f`).
4. The compiled string is stored in a `jsonpath` column, so Postgres rejects anything malformed at write time. The service additionally never executes `compiled_path` text it did not generate (the column is written only by the compiler).
5. The token and the jsonpath travel as **bound parameters**.

`compiler_version` (smallint) is stored with each policy; a compiler change bumps it and `uv run krep policy recompile` rewrites `compiled_path` from `ast` for all rows.

| 5 | `{"token":{"roles":["admin","user"]}}` | `token.roles != "admin"` | false |
| 6 | `{"token":{"clearance":3}}` | `token.clearance >= 3` | true |
| 7 | `{"token":{"clearance":"3"}}` | `token.clearance >= 3` | false (no coercion) |
| 8 | `{"token":{"https://acme.com/roles":["admin"]}}` | `"admin" in token["https://acme.com/roles"]` | true |
| 9 | `{"token":{"tid":"t1"}}`, vars `{"tenant_id":"t1"}` | `token.tid == var.tenant_id` | true (false with `t2`) |
| 10 | `{"token":{"email":"a@acme.com"}}` | `token.email.endsWith("@acme.com")` | true |
| 11 | `{"token":{"nul":null}}` | `token.nul == null` | true |
| 12 | contractor doc: `{"token":{"department":"billing","roles":["manager"],"groups":["contractors"]}}` | rule 12 above | false (true without the `contractors` group) |
| 13 | `{"token":{},"principal":{"roles":["support"]}}` | `"support" in principal.roles` | true |

### 8.4 Evaluation in SQL (policies first, then resources)

A tenant has tens or hundreds of policies but possibly thousands of resources. So the caller's document is evaluated against the **policies** (one cheap pass), and resources are filtered by `policy_id IN (satisfied policies)`. No resource is ever evaluated individually and nothing is filtered in the application.

```sql
WITH sat AS MATERIALIZED (
  SELECT p.id
  FROM access_policies p
  WHERE p.tenant_id = :tenant
    AND jsonb_path_match(:doc::jsonb, p.compiled_path, :vars::jsonb, true)   -- true = silent: errors count as not satisfied
)
SELECT ... FROM registry r
WHERE r.visibility = 'restricted' AND r.policy_id IN (SELECT id FROM sat)
```

- `:doc` = `{"token": ..., "principal": ...}` (4.3); `:vars` = `{"tenant_id": "<uuid>"}`.
- Cost scales with the number of policies per tenant (limit key `max_policies`, default 500), not resources. Measured: 300 policies of about 8 leaves against a 40-group token take about 0.14 ms (section 12).
- Optional later: cache the satisfied set per (tenant, token hash, policies version) for about 60 s.
- Get-by-id evaluates only that resource's one policy.

### 8.5 Worked example

Policy "Billing leads or admins (no contractors)" as authored:

```text
token.department == "billing"
  && ("manager" in token.roles || "support-lead" in token.roles)
  && !("contractors" in token.groups)
```

Callers (evaluation document -> result):

| Caller `token` | Result | Why |
| --- | --- | --- |
| `{"department":"billing","roles":["manager"],"groups":["eng"]}` | visible | all three parts hold |
| `{"department":"billing","roles":"support-lead"}` | visible | scalar role works; no `groups` claim so the NOT holds |
| `{"department":"billing","roles":["manager"],"groups":["contractors"]}` | hidden | `contractors` present |
| `{"department":"sales","roles":["manager"]}` | hidden | department differs |
| `{"roles":["manager"]}` | hidden | no `department` claim (missing = false) |

Same rule for a customer whose backend sends a principal: `principal.department == "billing" && ("manager" in principal.roles || "support-lead" in principal.roles) && !("contractors" in principal.groups)`.

### 8.6 Policy management

Table: `access_policies` (`ast` is the source of truth, `source` and `compiled_path` are derived). Admins only. Policies are tenant-level objects referenced by resources through `registry.policy_id`.

| Method + path | Purpose |
| --- | --- |
| `POST /v1/access-policies` | create (name unique per tenant); body has `source` **or** `ast` |
| `GET /v1/access-policies` / `/{id}` | list; get with `ast`, `source`, `compiled_path`, `rev`, `summary`, `usage_count` |
| `PUT /v1/access-policies/{id}` | replace `name`, `description`, `source`/`ast`; requires `rev` |
| `DELETE /v1/access-policies/{id}` | `409 policy_in_use` while any resource references it; reserved policies cannot be deleted |
| `GET /v1/access-policies/{id}/resources` | resources using it (drives "affects N resources") |
| `GET /v1/access-policies/{id}/history` | last 20 revisions |
| `POST /v1/access-policies/{id}/restore` | `{"rev": 3}` writes a new revision with that rule |
| `POST /v1/access-policies/{id}/test` | evaluate a pasted sample token/principal; no persistence |
| `POST /v1/access-policies/preview` | parse + compile an unsaved rule; returns ast, compiled path, warnings, summary |

Create/update transaction: parse (text) or validate (ast) -> compile -> if update: check `rev` (`409 rev_conflict` on mismatch) -> write `ast`, `source` (regenerated from the AST), `compiled_path`, `compiler_version` -> bump `rev` -> insert `access_policy_history` -> delete history older than the newest 20. ```

### 8.7 Visibility change rules

- Setting `visibility = restricted` requires `policy_id` (DB CHECK). Switching away from restricted leaves `policy_id` untouched (kept for convenience) but it is ignored by discovery.
- Archiving or unpublishing never changes visibility.
- `private` is the default for new resources.

```json
    { "id": "0b8f...", "type": "agent", "slug": "refund-assistant", "name": "Refund Assistant",
      "description": "Handles refund requests up to 500 USD...", "tags": ["billing","refunds"],

  ],
  "limit": 10, "offset": 0
}
```

No total count in V1 (avoids a second query and any count-based leakage; the next page is simply empty).

### 9.2 What search does (no embeddings)

Two branches over the rows the caller may see, merged by Reciprocal Rank Fusion:

- **Lexical:** Postgres full-text search with English stemming over `name` (weight A), `description` (B) and `tags` (C). Words are combined with **OR**, ranked by `ts_rank_cd`, so a resource matching more of the query words ranks higher.
- **Fuzzy name:** `pg_trgm` `word_similarity` against `name` only (threshold 0.3), which catches typos and partial words.

Examples (verified on 10,000 synthetic rows):

| Query | Result |
| --- | --- |
| `refunds` | finds "refund" agents (stemming) |
| `refnd` | finds "refund" agents (fuzzy name; needs threshold 0.3) |
| `money back returned` | ranks "Refund Assistant" first through the words in its description (OR query) |
| a word that never appears in any name/description/tag/synonym (for example `reimbursement` vs "refund") | no match; add a synonym group (9.4) or enable semantic search (7.6) |

**Query building** (service layer, before SQL):

1. Normalise: lowercase; replace every character that is not a letter, digit or underscore with a space; collapse spaces; at most 12 tokens; `q_norm` = tokens joined by single spaces (<= 100 chars).
2. Expand with the tenant's synonym groups (9.4).
3. Build `tsq`: single words as-is, multi-word phrases as `(w1 <-> w2)`, all joined with ` | `. Because tokens contain only letters, digits and underscores, no tsquery operator can be injected; at most 30 terms after expansion.
4. If `tsq` is empty (only stop words or symbols) skip the lexical branch; if the fuzzy branch is also empty return an empty list.

### 9.3 Query (filter first, then rank)

Implement as `registry_search()`; all search code lives behind this one function so the engine could be swapped later. The transaction first runs `SELECT set_config('pg_trgm.word_similarity_threshold', '0.3', true)`.

```sql
WITH sat AS MATERIALIZED (            -- policies this caller satisfies (8.4)
  SELECT p.id FROM access_policies p
  WHERE p.tenant_id = :tenant
    AND jsonb_path_match(:doc::jsonb, p.compiled_path, :vars::jsonb, true)
), visible AS MATERIALIZED (
  SELECT id, name, search_tsv
  FROM registry r
  WHERE r.tenant_id = :tenant AND r.status = 'published'
    AND (:type IS NULL OR r.type = :type)
    AND (:tags::text[] IS NULL OR r.tags @> :tags)
    AND ( r.visibility = 'tenant'
       OR (r.visibility = 'private' AND r.created_by = :user)
       OR (r.visibility = 'restricted' AND r.policy_id IN (SELECT id FROM sat)) )
), lex AS (
  SELECT id, row_number() OVER (ORDER BY ts_rank_cd(search_tsv, q) DESC) AS rnk
  FROM visible, to_tsquery('english', :tsq) q
  WHERE search_tsv @@ q
  LIMIT 50
), fuzzy AS (
  SELECT id, row_number() OVER (ORDER BY word_similarity(:q_norm, name) DESC) AS rnk
  FROM visible
  WHERE :q_norm <% name
  LIMIT 50
)
SELECT v.id,
       COALESCE(1.0/(60 + lex.rnk), 0) + COALESCE(1.0/(60 + fuzzy.rnk), 0) AS score
FROM visible v LEFT JOIN lex ON lex.id = v.id LEFT JOIN fuzzy ON fuzzy.id = v.id
WHERE lex.id IS NOT NULL OR fuzzy.id IS NOT NULL
ORDER BY score DESC, v.id
LIMIT :limit OFFSET :offset;
```

Notes:

- The visibility filter comes first, so both branches only see rows the caller may see; pages are exact.
- Trigram matching is on `name` only. On the same 10,000 rows, adding `description` made the query about 8x slower (41 ms vs 4.8 ms).
- RRF constant 60. Branch depth 50 (so `offset + limit <= 100` is fully ranked; deeper offsets return what the branches produced).
- Hydrate `items` with a second query by ids (`name`, `description`, `tags`, `current version number`).
- The query `q` empty case skips both branches and lists visible rows by `updated_at desc`.

### 9.4 Synonyms (tenant-curated, query-side)

A synonym group is a set of **2-10 equivalent terms** (words or phrases of up to 3 words, lowercase), per tenant. Example: `["refund", "money back", "reimbursement"]`. A search for `reimbursement` also searches `refund` and `money back`, and vice versa.

How it stays small and maintainable:

- **Query-side only.** Stored text is never changed, so adding or editing a group takes effect immediately with no reindexing.
- **Bounded.** `max_synonym_groups` (default 200 per tenant, via `resource_limits`).
- **Symmetric, not transitive.** A group expands every member to every other member; `A~B` and `B~C` in different groups do **not** imply `A~C`, so groups cannot drift into each other.
- **Admin-curated.** No automatic generation. The signal for what to add is missed searches: V1 exposes a per-tenant counter metric `search_zero_results_total` and, when `SEARCH_LOG_ZERO_RESULTS=true` (default false, because queries can contain sensitive text), logs the normalised query (<= 100 chars) of searches that returned nothing.
- **Cached** per tenant in the service (term -> group index), refreshed on write and every 60 s.
- Easy to drop: if it is not wanted, remove the table, the API rows and step 2 of query building; nothing else depends on it.

API (admin only): `GET /v1/search/synonyms`, `POST /v1/search/synonyms`, `PUT /v1/search/synonyms/{id}`, `DELETE /v1/search/synonyms/{id}`.

```json
POST /v1/search/synonyms
{ "terms": ["refund", "money back", "reimbursement"] }
-> 201 { "id": "5b0e...", "terms": ["refund", "money back", "reimbursement"] }
```

Errors: `422 validation_failed` (fewer than 2 or more than 10 terms, a term over 3 words, characters other than letters, digits and spaces after normalisation), `409 synonym_group_exists` (same set of terms), `409 synonym_limit_reached` at the cap (200 groups).

### 9.5 Get by id

`GET /v1/registry/{id}` applies the same visibility predicate (single row) and returns resource fields plus current version summary, `404` if not visible.

## 12. Performance

**Measured** (local Docker, PostgreSQL 17, 4 concurrent clients, synthetic data: 10,000 resources in one tenant, 30% restricted, 300 policies, a token with 40 groups; no embeddings):

| What | Result |
| --- | --- |
| Policy evaluation (`sat` CTE) for the caller | 0.14 ms average (about 27,000 per second) |
| Full search, one-word query (policy evaluation + visibility filter + lexical + fuzzy + RRF, top 10) | 7.6 ms average |
| Full search, three-word OR query | 10.4 ms average |
| Fuzzy matching on `name` vs on `name` and `description` (lexical + fuzzy only) | 4.8 ms vs 41 ms |

These are synthetic numbers on one container; the benchmark task (build step 9) reruns them in CI.

**Targets (p95, tenant with 10,000 resources):**

- Search <= 100 ms with the access filter active.
- Policy save (parse + compile + write) <= 100 ms for a 100-node rule.
- Bundle resolution (depth 3, 10 deps) <= 30 ms.

**Scaling levers, in order:** (1) cache the satisfied-policy set per (tenant, token hash, policies version) for about 60 s; (2) cap query terms (already 30 after expansion); (3) add semantic search only if the evaluation in 7.6 shows it is needed. ## 14. Acceptance tests (must pass)

Isolation and identity:

1. Tenant A cannot read, search, or link tenant B rows, even with a forged `tenant_id` in the body (RLS; tests connect as `krep_app`, never as the owner or a superuser).
2. Tenant resolution: an issuer with a fixed `tenant_id` and an issuer with a `tenant_claim_path` both resolve correctly; a token from an unregistered issuer or wrong audience returns `401`.
3. Principal trust: a mode B/C caller with `allow_principal` has its `X-Principal` honored (user id = `principal.id`); a mode A user token sending `X-Principal` has it ignored; a principal without `id` returns `400 principal_id_required`.
4. Reserved policies: with no `registry-admins` / `registry-writers` policy nobody can write or administer; after `krep tenant init` the rules grant exactly the callers they describe.

Discovery and access:

5. Visibility matrix: for `private`, `tenant`, `restricted` x (creator, same-tenant other user, rule-matching caller, other tenant) outcomes match 8.1 and the 8.5 table.
6. Hidden resource returns `404` on get-by-id and is absent from search; no total counts are returned.
7. Search recall with filter: tenant has 500 agents, caller can see 20, 12 of which match "refund"; page 1 (limit 10) returns 10 visible matches and page 2 returns the remaining 2.
8. A policy that errors at evaluation time (forced in a test) counts as not satisfied; the resource is hidden, the request still succeeds.

Policies:

9. All golden compiler tests (15) and Postgres semantic tests (13) in 8.3 pass.
10. Injection: a rule whose literal is `"); DROP TABLE registry; --` or whose key is `a"."b` is stored, compiled with escaping, evaluates correctly, and executes no extra SQL.
11. Editing a policy re-evaluates all referencing resources immediately; stale `rev` returns `409 rev_conflict`; history keeps only the last 20; restore creates a new revision.
12. Deleting an in-use policy returns `409 policy_in_use`; reserved policies cannot be deleted or renamed.
13. `POST .../test` with a pasted token reports per-leaf results and the type-mismatch, absent-claim and group-overage warnings.

Versions:

14. Updating any column of a published version or its subtype row fails (trigger).
15. Publishing the 11th version deletes the oldest non-current version when unreferenced, and returns `409 version_in_use` (with referrers, nothing changed) when it is pinned by a link or depended on by another version.
16. Draft cap: the 51st draft in one tenant/type returns `409 draft_limit_reached`; concurrent creates cannot exceed 50 (advisory lock test with parallel requests).
17. Overriding a limit by inserting a tenant-scoped `resource_limits` row changes behaviour with no code change.
18. Repointing current to an older retained version works; deleting the current version is rejected.

Links:

19. Skill-initiated link on someone else's agent is `pending`, invisible to auto-load, and becomes active only after the agent owner accepts.
20. Publishing agent v7 freezes `registry_version_deps` to skill v4; publishing skill v5 afterwards does not change v7's bundle.
21. Creating a link that would form a cycle returns `422 link_cycle`; a pair not in `link_rules` returns `422 link_not_allowed`.
22. Deleting a skill that agents link to returns `409 resource_in_use` with the referrers.

Misc:

23. Search quality (9.2 examples): `refunds` finds "refund" agents; `refnd` finds them through fuzzy name matching; `money back returned` ranks the resource whose description has those words first.
24. Synonyms: with group `["refund","money back","reimbursement"]`, searching `reimbursement` finds a resource that only says "refund"; removing the group removes the effect immediately; the 201st group returns `409 synonym_limit_reached`; groups are not transitive.
25. Query safety: queries containing tsquery syntax or symbols (`refund | ) & !`, `'"; --`, only stop words) never raise an error and return a normal (possibly empty) list.
26. Zero-result searches increment `search_zero_results_total` for the tenant; the normalised query is logged only when `SEARCH_LOG_ZERO_RESULTS=true`.
27. A new resource type added per 5.3 can be created, versioned and searched with no change to `registry`, search, or policy code.
28. `alembic upgrade head` on a fresh database succeeds, and `alembic downgrade base` followed by `upgrade head` succeeds again.
